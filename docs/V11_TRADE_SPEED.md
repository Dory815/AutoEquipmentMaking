# v1.1 RC.6 村民交易优化

2026-10-24。用户要求减少绿宝石数量调整的耗时。所有运行验证使用项目独立单人存档，不连接 201，不操作原 PCL/Dory 客户端。

## 原因与接口

RC.5 每买一件都会重新选择报价。选择报价时，原版服务端自动从整个背包填入货币。旧代码先把全部自动填料逐槽还原，再用 `Robot.Put` 放入精确价格。`Robot.Move` 对部分堆叠使用逐颗右键。例如从 64 颗中拿 60 颗会产生 62 次点击。这些动作逐次等待服务端确认，因此服务器延迟会进一步放大耗时。

检查对象是本地 Minecraft 26.2 的实际游戏类。`ServerGamePacketListenerImpl.handleSelectTrade` 调用 `MerchantMenu.setSelectionHint` 和 `tryMoveItems`。`tryMoveItems` 填充付款槽，不能通过该选择包关闭自动填料。`MerchantResultSlot.onTake` 调用 `MerchantOffer.take`，只扣除报价要求的数量，付款槽不必精确等于价格。

因此继续使用原版选择包和容器点击接口，不新增客户端或服务端依赖。Servux 仍只读取报价与库存，不执行购买。没有使用不受数量约束的交易结果 Shift 点击。

## 改动

- 选择后核对全部库存减少量与付款槽数量。只退回自动填料挪用的私人货币，保留任务货币。
- 同种商品在一个菜单中连续购买，数量上限为当前采购目标缺口。
- 每次取结果前复核报价、商品和私人槽位。每次取结果后，必须确认光标中的商品以及两个付款槽的准确减少量。
- 钱或普通书不足时从任务背包补堆叠。没有足够任务资金时退出该菜单，由原有补货流程继续。
- 付款移动优先使用整组或半组点击；其他数量选择“放入目标数量”与“退回剩余数量”中点击更少的一种。每次点击都等服务端确认。
- 结束、达到报价次数上限或预算上限时，先把付款槽余量明确退回任务槽位，再关闭菜单。关闭菜单的原版自动归还会向私人堆叠合并，因此不依赖该行为。
- 两个付款槽收取相同物品的特殊自定义报价保留精确填料分支。普通附魔书、弓和盾牌走新路径。

主要代码：`client/src/main/java/io/github/autoequipmentmaking/client/Trading.java`。通用制作、锻造和附魔的 `Robot.Move` 不变。

## 测试范围

`TradingGameTest` 检查绿宝石/普通书缺货、good 门禁、手动暂停、20 秒补货冷却、64 颗报价和私人货币保护。追加场景预备三本书的全部资金，要求只选择一次报价、只使用一个菜单、恰好买三本，并准确退回剩余货币。

`AllBooksProcurementGameTest` 使用与 RC.5 相同的全书采购场景：原料没有附魔书，3 个村民提供 55 本附魔书及弓盾，交易次数上限 1,000。全部购买必须先于领取钻石原料，随后通过实际菜单完成 14 件装备和 1 盒交付。追加断言要求连续交易复用菜单，并在每笔付款前保留私人货币数量。

测试第一次运行发现 64 颗报价下的部分堆叠循环：退回不足一组的付款后又拿起同一堆，仍无法填满付款槽。该次人工停止，不计通过。记录位于 `docs/evidence/v11-rc6-trading-attempt1-*`。修正为直接合并部分数量，并加入较少点击拆分。
