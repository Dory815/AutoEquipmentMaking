# ADR 0001 选择客户端执行

日期：2026-10-23。决定：本项目 v1.0–v1.2 采用客户端 Fabric 模组。

## 背景

用户可以修改 Servux 配置，但按不能安装新服务端模组规划。用户允许机器人独占玩家账号。现有服务器安装 Carpet 和 Servux，并允许被方块阻挡的潜影盒打开。

## 比较

| 维度 | 客户端模组 | 服务端模组与 Carpet 假人 |
|---|---|---|
| 当前部署 | 满足限制，使用现有 Servux | 需要安装本项目服务端模组，当前不满足条件 |
| 库存读取 | 依赖 Servux 或实际打开菜单 | 可在服务端直接读取受权限限制的库存 |
| 槽位和费用 | 必须等待服务器确认，防止预测错误 | 可直接调用服务端菜单逻辑，更容易确认结果 |
| 长期运行 | 依赖客户端持续在线，账号由机器人占用 | 服务器在线时可持续运行，不占用真实客户端 |
| 移动 | 驱动玩家输入，管理视线、距离、网络校正 | 驱动假人移动；假人不会自动拥有寻路 AI |
| 经验 | 使用真实玩家等级，来源明确 | 需要为假人提供经验，不能默认继承操作者经验 |
| 版本耦合 | Fabric、菜单、Servux、现有客户端模组 | Fabric、Carpet 假人内部结构、服务端菜单和插件 |
| 失败影响 | 通常局限于当前客户端与任务资产 | 服务端错误可能影响全服，部署与升级更严格 |
| home 兼容 | 使用真实玩家已有命令权限 | 假人的身份、权限、home 插件兼容必须另外验证 |
| Servux 价值 | 对远程读取原料箱有直接作用 | 原生服务端执行通常不需要 Servux |
| 本项目选择 | 当前推荐并采用 | 未来部署条件允许时再考虑 |

## 为什么现有 Carpet 不能直接替代

Carpet 的假人提供服务器玩家实体与动作基础，不提供寻找库存、最省等级附魔、GUI 生产事务和礼包装箱的整套流程。仍需编写自定义逻辑。

即使尝试 Scarpet 脚本，也需要脚本部署权限、脚本实现和兼容验证。它不是现有规则一键启用的能力，也不满足本轮按 Fabric Java 模组规划的统一实现方式。

## 后果

规划内核保持独立，未来可以复用。当前优先验证 Servux 与现有 MiniHUD/Tweakeroo 的共存。客户端掉线会中断生产，故障恢复是 v1.0 的必要条件。

如果以后服务器允许新增模组，并且目标变为无人值守长期批量生产，服务端路线在状态确认和持续运行上更合适。届时新增适配器，不将两套执行器塞入同一个客户端版本。
